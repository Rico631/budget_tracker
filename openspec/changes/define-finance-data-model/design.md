# Design

## Context

Сейчас `AppDatabase` на базе Drift открывает локальную SQLite-базу без предметных таблиц; schema version равен 1. Приложение использует Flutter, Riverpod и разделение на UI, data и domain слои. См. `proposal.md` и `specs/local-finance-data-model/spec.md` для мотивации и поведенческого контракта.

## Goals / Non-Goals

**Goals:**

- Добавить расширяемую локальную схему финансовых данных в существующий Drift database module.
- Сохранить изоляцию всех предметных сущностей через `book_id`.
- Представить перевод одной транзакцией с необязательным `to_account_id`.
- Разделить database tables, data-модели, repositories и domain/use case проверки.
- Подготовить тестируемые правила расчета балансов и валидации операций без UI-зависимости.

**Non-Goals:**

- Синхронизация, backend, авторизация и участники книги.
- Отдельная сущность или таблица переводов.
- Учет долгов, займов, обязательств и автоматических банковских импортов.
- Поддержка нескольких категорий внутри одной операции.
- Полноценные экраны управления финансами.

## Decisions

### Таблицы и связи

Добавляются следующие Drift tables:

- `Books`: `id`, `name`, `created_at`, `updated_at`, `is_archived`.
- `Banks`: `id`, `name`, необязательные реквизиты отображения, `is_archived`.
- `Accounts`: `id`, `book_id`, `bank_id`, `name`, `currency_code`, `initial_balance_minor`, `created_at`, `updated_at`, `is_archived`.
- `Categories`: `id`, `book_id`, `name`, `kind` (`income` или `expense`), необязательный `parent_id`, `created_at`, `updated_at`, `is_archived`.
- `Transactions`: `id`, `book_id`, `account_id`, необязательный `to_account_id`, необязательный `category_id`, `kind` (`income`, `expense` или `transfer`), `amount_minor`, `occurred_at`, необязательное `note`, `created_at`, `updated_at`.

Все идентификаторы предметных записей имеют UUIDv7 в каноническом текстовом представлении. Генерация выполняется библиотекой `uuid` через импорт `package:uuid/uuid.dart` и вызов `Uuid().v7()`. UUIDv7 содержит временную составляющую и сохраняет приблизительный порядок создания записей, что уменьшает фрагментацию индексов SQLite по сравнению со случайным UUIDv4. Идентификатор генерируется один раз при создании записи и не изменяется при редактировании. `created_at` хранится отдельно, поскольку UUID используется как технический ключ, а время создания является бизнес- и аудиторским атрибутом. Внешние ключи и индексы должны поддерживать выборку по книге, счету и дате операции. `bank_id` остается nullable, чтобы поддержать наличные счета без искусственной записи «Наличные» в справочнике банков.

### Денежные значения

Денежные значения хранятся в минимальных единицах валюты как целые числа (`amount_minor`, `initial_balance_minor`). Floating point для денег не используется. В первой версии счет имеет одну `currency_code`, а перевод между счетами с разными валютами не разрешается, пока не появится модель курса и конвертации.

### Инварианты транзакций

Проверки согласованности выполняются в domain/use case слое до записи и дополнительно защищаются database-level ограничениями там, где это возможно:

```text
income:
  account_id != null
  to_account_id == null
  category_id -> category.kind == income

expense:
  account_id != null
  to_account_id == null
  category_id -> category.kind == expense

transfer:
  account_id != null
  to_account_id != null
  account_id != to_account_id
  category_id == null
  source and target belong to the same book
```

Сумма всегда положительная. Доход увеличивает баланс `account_id`, расход уменьшает его. Перевод уменьшает баланс `account_id` и увеличивает баланс `to_account_id`; поэтому общий баланс книги от перевода не меняется. Удаление и редактирование операции выполняются атомарно.

### Слои Flutter

```text
Flutter UI
    |
Riverpod providers
    |
domain use cases: create/update/delete transaction, calculate balance
    |
repositories
    |
Drift tables and AppDatabase
    |
SQLite
```

UI не обращается к Drift напрямую. Repositories предоставляют потоковые или одноразовые операции по книгам и дочерним сущностям. Use cases централизуют правила типа операции, принадлежности книге, категории и расчета баланса. Для UUIDv7 используется уже подключенная runtime-зависимость `uuid`; дополнительные зависимости не требуются.

### Миграция базы

`schemaVersion` увеличивается с 1 до 2. В `onUpgrade` создаются новые таблицы и индексы; существующие данные фундамента не преобразуются, поскольку на текущем этапе прикладных таблиц нет. Генерируемые Drift-файлы обновляются build_runner. До начала записи прикладных данных тесты должны проверять создание схемы на in-memory database.

## Risks / Trade-offs

- **[Risk]** Текстовые UUIDv7 увеличивают размер индексов по сравнению с integer ID, а несколько записей в одну миллисекунду не образуют строгую последовательность. **Mitigation:** UUIDv7 дает временно упорядоченный ключ и независимость локальных записей от будущей синхронизации; строгий порядок задается отдельными полями времени и сортировки.
- **[Risk]** Проверки только в domain-слое могут быть обойдены прямым вызовом database API. **Mitigation:** ограничить использование database module data-слоем и добавить интеграционные тесты на недопустимые комбинации полей.
- **[Risk]** Смешение валют нарушит расчет баланса. **Mitigation:** запретить переводы между разными валютами до появления явной модели конвертации.
- **[Risk]** Удаление книги или счета может оставить осиротевшие операции. **Mitigation:** использовать внешние ключи, архивирование как основной пользовательский сценарий и атомарные операции удаления.

## Migration Plan

1. Добавить Drift tables, перечисления и индексы.
2. Увеличить schema version и реализовать миграцию с версии 1.
3. Сгенерировать Drift-код.
4. Добавить data-модели, repositories и domain use cases с валидацией инвариантов.
5. Подключить Riverpod providers для доступа к repositories.
6. Проверить in-memory миграцию, CRUD, расчет балансов и отклонение некорректных операций.

Откат выполняется возвратом приложения к версии без предметных таблиц только до появления пользовательских данных. После начала использования версии 2 откат без потери данных не предусматривается; изменения схемы должны быть обратимо мигрируемыми или сопровождаться резервным экспортом базы.
