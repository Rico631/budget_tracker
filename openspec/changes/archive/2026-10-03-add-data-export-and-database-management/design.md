# Design

## Context

Согласно ADR-0001 (решение 4.5) локальный экспорт и резервное копирование входят в продукт, а «формат и место экспорта/резервной копии» остаются отложенным вопросом. Импорт банковских операций запрещён (ADR-0001, решение 1.3) и в это изменение не входит. База приложения — Drift, один файл `budget_tracker.sqlite` в каталоге application support, открываемый через `drift_flutter` ([app_database.dart](c:/Users/rico/StudioProjects/budget_tracker/lib/data/local/database/app_database.dart:190)); `schemaVersion = 5`, денежные суммы хранятся целыми в минорных единицах. Инициализация первого запуска создаёт книгу, стартовые категории, банки и валюты, а её признак хранится в таблице `AppSettings` внутри самой базы ([first_run_bootstrap_repository.dart](c:/Users/rico/StudioProjects/budget_tracker/lib/data/repositories/first_run_bootstrap_repository.dart:20)). Мотивация изменения — в `proposal.md`.

## Goals / Non-Goals

**Goals:**

- Выгрузка журнала операций в один CSV-файл, открываемый в Excel двойным кликом в обеих локалях.
- Резервная копия данных одним согласованным файлом `.sqlite` и восстановление из него без риска для текущих данных.
- Управление несколькими базами: реестр, список, переключение активной, удаление; мягкий перезапуск при смене базы.

**Non-Goals:**

- Импорт CSV и импорт банковских выписок (ADR-0001, 1.3).
- Облачная синхронизация, передача копий по сети (остаются вне продукта по ADR-0001).
- Полный перезапуск процесса через сторонний пакет: используется мягкий перезапуск.
- Изменение схемы базы: `schemaVersion` остаётся равным 5.

## Decisions

### 1. Два независимых направления: CSV export-only и SQLite backup/restore

CSV-выгрузка односторонняя и решает задачу «посмотреть данные вне приложения»; резервное копирование и восстановление решают задачу «не потерять данные» через файл `.sqlite`. Совмещать их в одном формате нельзя: CSV без потерь не описывает 7 таблиц со связями и `isFallback`, а восстановление базы из CSV было бы best-effort. Альтернатива «один CSV и для восстановления» отвергнута из-за необратимых потерь ссылок и признаков.

### 2. Реестр баз — внешний JSON-файл

Активная база хранится вне самих баз: `db_registry.json` в каталоге application support рядом с файлами баз. Указатель не может жить в `AppSettings`, потому что `AppSettings` находится внутри переключаемой базы. Формат: `{ "version": 1, "activeId": "...", "entries": [ { "id", "fileName", "createdAt", "source" } ] }`, где `fileName` — имя файла относительно каталога application support, `source` — `original` / `imported` / `backup`. Альтернативы: `shared_preferences` (+1 зависимость ради одного поля) и отдельная SQLite-БД метаданных (избыточно) — отвергнуты.

### 3. Расположение файлов баз и миграция существующих установок

Файлы баз остаются в каталоге application support (там уже лежит `budget_tracker.sqlite`): исходная база сохраняет имя `budget_tracker.sqlite`, импортированные копии получают имена с меткой времени (`import_<timestamp>.sqlite`). Это уточняет формулировку «подпапка databases» из обсуждения: без переноса существующего файла и без отдельной подпапки, чтобы не ломать установленные приложения. При первом запуске после обновления, если `db_registry.json` отсутствует, реестр создаётся с единственной записью — текущей базой как активной. Реестр не обязан существовать до первого входа в раздел управления базами.

### 4. Резервная копия — `VACUUM INTO`

Снимок создаётся SQL-командой `VACUUM INTO '<path>'` в выбранную пользователем точку. Это даёт согласованный однофайловый снимок без хвоста WAL и без блокировки записи — в отличие от копирования основного файла, которое при включённом WAL может захватить неполное состояние. Выбранный путь — результат SAF-диалога `file_picker.saveFile`; после `VACUUM INTO` данные текущей базы не изменяются.

### 5. Конвейер восстановления: копия → валидация → миграции → переключение

Восстановление не трогает текущую базу до последнего шага:

1. `file_picker.pickFiles` выбирает файл;
2. байты копируются в каталог application support под именем `import_<timestamp>.sqlite`;
3. кандидат валидируется: файл открывается отдельным экземпляром `AppDatabase` по явному пути; проверяются `PRAGMA user_version` (не выше `schemaVersion` приложения, то есть 5) и наличие ожидаемых таблиц через `sqlite_master`; открытие само доигрывает миграции, если версия ниже;
4. работоспособность подтверждается пробным чтением (например, `SELECT` по `Books`);
5. только после успеха в реестре обновляется `activeId` на новую запись, и выполняется мягкий перезапуск.

При любом отказе на шагах 2–4 временная копия удаляется, активная база и реестр не меняются, пользователь видит сообщение с причиной. Версия выше поддерживаемой отклоняется (миграция «вниз» невозможна).

### 6. Мягкий перезапуск без нового пакета

Корень приложения ([main.dart](c:/Users/rico/StudioProjects/budget_tracker/lib/main.dart:31)) оборачивается в перезапускаемый корневой виджет, владеющий `ProviderContainer`. По команде перезапуска контейнер освобождается (существующий `ref.onDispose(database.close)` закрывает соединение), создаётся новый контейнер с `AppDatabase`, открытым по новому активному пути, и дерево `MaterialApp` пересобирается. Активный путь читается из реестра до `runApp` и передаётся как стартовое значение. Альтернатива `flutter_phoenix`/`restart_app` отвергнута как лишняя зависимость.

### 7. Открытие базы по явному пути

`AppDatabase` получает необязательный параметр `filePath`; при его отсутствии сохраняется текущее поведение `driftDatabase(name: 'budget_tracker')`. Провайдер `appDatabaseProvider` ([finance_providers.dart](c:/Users/rico/StudioProjects/budget_tracker/lib/core/di/finance_providers.dart:10)) открывает базу по пути, предоставленному стартовым значением. Заводское состояние после удаления единственной базы обеспечивается существующим first-run bootstrap: у новой пустой базы нет признака `first_run_completed`, поэтому [AppBootstrapGate](c:/Users/rico/StudioProjects/budget_tracker/lib/presentation/features/bootstrap/app_bootstrap_gate.dart) создаёт книгу и справочники штатно.

### 8. CSV-генератор — чистая функция без CSV-зависимости

Сервис доменного слоя формирует строку CSV из списка операций и денормализованных имён счёта/валюты/категории. Профиль задаётся структурой `{ columnSeparator, decimalSeparator, headers, kindLabels }`, выбираемой по языку выгрузки: `ru` → `;`, `,`; `en` → `,`, `.`. Экранирование — стандартное: поле, содержащее разделитель, кавычку или перевод строки, заключается в кавычки, кавычки удваиваются. Числа записываются из минорных единиц в десятичные без разделителей групп. Даты — ISO `yyyy-MM-dd HH:mm:ss`. Зависимость `csv` не добавляется: генератор мал, а правило экранирования — часть контракта формата. Файл пишется как `UTF-8` с BOM.

### 9. Чтение журнала для выгрузки — отдельный запрос

Для денормализации без N+1 добавляется метод чтения в слой данных (запрос `Transactions` с join к `Accounts` и `Categories`), возвращающий готовые строки журнала. UI и доменный сервис не знают о SQL.

### 10. Новая зависимость `file_picker`

Добавляется одна зависимость `file_picker` для SAF-диалогов `saveFile` (выгрузка CSV и резервная копия) и `pickFiles` (восстановление). Причина: на Android доступ к произвольным местам хранения без разрешений даёт только системный SAF. Share sheet (`share_plus`) отложен, чтобы не добавлять две зависимости сразу.

### 11. UI — хаб в настройках

В [settings_page.dart](c:/Users/rico/StudioProjects/budget_tracker/lib/presentation/features/settings/settings_page.dart) добавляется пункт «Экспорт и базы данных», открывающий подэкран с четырьмя пунктами: выгрузка журнала (диалог с селектором языка и кнопкой), резервная копия, восстановление из копии, список баз. Подэкран списка баз реализует контракт D3: бейдж «Текущая», действия «Сделать активной» и «Удалить» для неактивных, запрет удаления активной (кроме единственной — с созданием новой базы). В строке базы показываются дата и время создания из реестра на языке приложения: время нужно, чтобы различать базы, созданные в один день. Все новые строки добавляются в ARB-файлы обеих локалей.

### 12. Имена файлов выгрузки — одна маска

CSV-журнал и снимок базы получают имя по одной маске `bt_YYYYMMDDHHmmss` (расширение `.csv` или `.sqlite`) из общего правила `exportFileName`. Общий префикс отличает файлы приложения от посторонних, а метка времени до секунд делает имена уникальными и сортируемыми. Имя импортированной копии при восстановлении остаётся прежним (`import_YYYYMMDD_HHmmss.sqlite`), чтобы по имени было видно происхождение базы.

### 13. Новая ADR

Согласно `openspec/config.yaml`, при изменении глобальной архитектуры добавляется запись в `docs/adr/`: создаётся `0006-data-export-and-database-management.md`, фиксирующая формат CSV-журнала и его локализацию, снимок через `VACUUM INTO`, контракт восстановления, реестр баз и правила переключения/удаления. Это закрывает отложенный вопрос ADR-0001 «формат и место экспорта/резервной копии». Создание ADR вынесено отдельной задачей.

## Risks / Trade-offs

- [Снимок при WAL мог бы потерять свежие записи] → используется `VACUUM INTO`, а не копирование файла.
- [Повреждённый или чужой файл при восстановлении] → валидация версии и таблиц до переключения; текущая база не удаляется; страховочная копия не требуется, так как старая база сохраняется в списке.
- [Мягкий перезапуск может оставить закэшированное состояние провайдеров] → контейнер создаётся заново, а не инвалидируется; покрывается виджет-тестом переключения.
- [Реестр разъехался с файлами (файл удалён вне приложения)] → при чтении реестра отсутствующий файл активной базы отбрасывается, активной назначается первая доступная; реестр переписывается.
- [Импорт базы с версией выше поддерживаемой] → отказ с сообщением, миграция «вниз» не выполняется.
- [Десятичный знак и разделитель разъехались по локалям] → профиль выводится из выбранного языка выгрузки одним местом и проверяется golden-тестами.

## Migration Plan

Схема базы не меняется (`schemaVersion = 5`). Развёртывание для существующих установок: при первом запуске после обновления реестр `db_registry.json` отсутствует и создаётся отложенно с текущей базой `budget_tracker.sqlite` как активной; файл базы не переносится. Откат: удаление новой версии и возврат предыдущей оставляет базу в исходном месте и формате, так как формат данных не менялся.
