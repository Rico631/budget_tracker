# App Foundation

## Purpose

Capability предоставляет приложению устойчивый фундамент для локального хранения данных, управления состоянием и локализации. Он предназначен для того, чтобы последующие функции учета личных финансов могли использовать единые инфраструктурные правила.

## Requirements

### Requirement: Локальное хранилище доступно приложению

Приложение MUST предоставлять локальное хранилище на базе SQLite, доступное из data-слоя без зависимости UI от деталей открытия и размещения файла базы данных.

#### Scenario: Приложение запускается с доступным локальным хранилищем

- **WHEN** приложение запускается на поддерживаемом Android-устройстве
- **THEN** data-слой получает доступ к локальной базе данных без обращения к серверу
- **AND** временное закрытие и повторный запуск приложения не удаляют сохраненные данные

#### Scenario: Ошибка открытия локального хранилища

- **WHEN** база данных не может быть открыта или инициализирована
- **THEN** приложение обрабатывает ошибку контролируемо и не сообщает о готовности хранилища как о доступном

### Requirement: Состояние приложения имеет единый scope

Состояние и зависимости приложения MUST быть доступны виджетам через единый корневой scope, а провайдеры MUST допускать изолированную замену зависимостей в тестах.

#### Scenario: Виджет получает состояние из корневого scope

- **WHEN** виджет приложения читает или изменяет состояние через provider
- **THEN** операция выполняется в корневом scope приложения
- **AND** изменение состояния отражается в зависимых виджетах без ручной передачи состояния через конструкторы экранов

#### Scenario: Провайдер тестируется изолированно

- **WHEN** тест создает отдельный контейнер или scope с тестовой зависимостью
- **THEN** провайдер использует тестовую зависимость
- **AND** состояние теста не пересекается с состоянием другого теста или рабочего приложения

### Requirement: Пользовательские строки локализуются централизованно

Пользовательские строки приложения MUST храниться во внешних localization resources и предоставляться UI через стандартный Flutter localization API. На первом этапе приложение MUST поддерживать локали `ru` и `en`, используя `ru` как fallback locale.

#### Scenario: Приложение выбирает русский язык

- **WHEN** локаль устройства равна `ru` или совместима с `ru`
- **THEN** Material и пользовательские строки отображаются на русском языке

#### Scenario: Приложение выбирает английский язык

- **WHEN** локаль устройства равна `en` или совместима с `en`
- **THEN** Material и пользовательские строки отображаются на английском языке

#### Scenario: Локаль устройства не поддерживается

- **WHEN** локаль устройства отсутствует в списке поддерживаемых локалей
- **THEN** приложение использует русский язык как fallback locale
- **AND** UI не падает из-за отсутствующего перевода

#### Scenario: Русские и английские ресурсы синхронизированы

- **WHEN** разработчик добавляет строку в localization resources
- **THEN** строка присутствует в русском и английском ARB-ресурсах
- **AND** оба ресурса успешно проходят генерацию localization API

#### Scenario: Новая строка добавляется в localization resources

- **WHEN** разработчик добавляет строку в localization resources и запускает генерацию
- **THEN** приложение получает типобезопасный доступ к этой строке через сгенерированный localization API
- **AND** исходный UI-код не требует ручного выбора перевода по ключу локали
