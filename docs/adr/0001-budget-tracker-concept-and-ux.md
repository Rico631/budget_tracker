# ADR-0001: Концепция, модель учета и UX приложения budget_tracker

- **Статус:** Accepted
- **Дата:** 2026-09-26
- **Область:** продукт, семантика домена, навигация, представление данных, визуальный стиль
- **Источник решений:** 9 грилл-сессий `grill-me` по проекту `budget_tracker`, 29 решений, 29/29 ветвей закрыто
- **Связанные артефакты:** `openspec/specs/app-foundation/spec.md`, `openspec/specs/local-finance-data-model/spec.md`
- **Заменяет:** решение о запрете перевода между счетами в разных валютах из `openspec/changes/archive/2026-09-24-define-finance-data-model/design.md`

## Контекст

Проект `budget_tracker` — локальное (offline-first) Android-приложение на Flutter для учета личных финансов. К моменту фиксации решения уже реализованы фундамент приложения (`app-foundation`) и локальная модель финансовых данных (`local-finance-data-model`): Drift-таблицы `Books`, `Banks`, `Accounts`, `Categories`, `Transactions` на `schemaVersion` 2, идентификаторы UUIDv7, разделение UI / Riverpod / domain use cases / repositories / Drift.

Не были зафиксированы продуктовые и UX-решения: границы продукта, семантика счетов и валют, сценарий ручного ввода операций, поведение первого запуска, наполнение справочников банков и валют, представление аналитики и визуальный стиль.

Название пакета `budget_tracker` историческое: плановые бюджеты сознательно не входят в продукт (решение 1.2). Продукт — учет фактических операций и аналитика по ним, а не контроль лимитов.

Решения фиксировались методом `grill-me`: 9 сессий, по одной теме в каждой, ответы записывались в трекер сессий; все сессии закрыты со 100% отвеченных ветвей. Исходные plan-документы сессий создавались во временной директории ОС (`%TEMP%`) и не версионируются, поэтому их содержание перенесено в этот ADR — единственным носителем решения является этот документ.

## Решения

### 1. Продукт и его границы

Сессия: `budget-tracker-concept`.

| №   | Вопрос                                   | Решение                                                                                                                               | Обоснование и следствие                                                                                         |
| --- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 1.1 | Какую первичную задачу решает приложение | Управление счетами; учет доходов, расходов и переводов; просмотр текущих остатков и истории; аналитика по категориям за месяцы и годы | Продукт строится вокруг счетов как основной сущности и вокруг достоверности факта                               |
| 1.2 | Как задается план расходов               | Фиксируются только фактические операции и аналитика; плановые бюджеты и сравнение план/факт не входят в концепцию                     | Убирает целый пласт доменной модели (лимиты, периоды, прогресс) и снимает требования к экрану прогресса бюджета |
| 1.3 | Главный сценарий добавления операций     | Операции заносятся вручную; банковских интеграций не будет                                                                            | Нет импорта, сопоставления операций, внешних API и разрешений на доступ к банковским данным                     |
| 1.4 | Приоритет главного экрана                | Стартовый экран в первую очередь показывает список счетов с текущими остатками                                                        | Главный экран отвечает на вопрос «сколько денег сейчас», а не «сколько потрачено из лимита»                     |
| 1.5 | Платформы первой версии                  | Первая версия сначала для Android                                                                                                     | Синхронизация, аккаунты и серверная часть не проектируются; данные ведутся локально на устройстве               |

### 2. Детализация концепции: валюты, остатки, переводы, навигация

Сессия: `budget-tracker-detail`.

| №   | Вопрос                              | Решение                                                                                                                                                                                                                                                  | Обоснование и следствие                                                                                      |
| --- | ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 2.1 | Мультивалютность первой версии      | Каждый счет ведется в своей валюте. На экране счетов и в аналитике данные группируются по валютам; для группы показывается собственный итог без конвертации                                                                                              | Отсутствует модель курса и конвертации: суммы разных валют никогда не складываются в одно число              |
| 2.2 | Расчет текущего остатка счета       | Начальный остаток вводится отдельно при создании счета и не считается доходом                                                                                                                                                                            | Начальный остаток не искажает аналитику доходов; текущий остаток выводится из начального остатка и операций  |
| 2.3 | Учет переводов между своими счетами | Внутренний перевод учитывается в истории и остатках счетов, исключается из доходов/расходов и категорийной аналитики. При разных валютах пользователь вводит фактические суммы списания и зачисления; приложение вычисляет и показывает фактический курс | Перемещение собственных денег не считается заработком или тратой; курс вводится фактический, а не справочный |
| 2.4 | Структура основных разделов         | Основные разделы доступны в четырех нижних вкладках: Счета, Операции, Аналитика и Настройки; настройки — отдельная четвертая вкладка                                                                                                                     | Навигация плоская и предсказуемая, настройки не спрятаны внутрь другого раздела                              |
| 2.5 | Охват и фильтры аналитики           | Аналитика охватывает все счета книги по умолчанию, с возможностью фильтра по счету, категории и месяцу/году; суммы остаются раздельными по валютам                                                                                                       | Фильтр по счету/категории/периоду обязателен, а группировка по валютам действует при любом фильтре           |

### 3. Ручной ввод операций

Сессия: `budget-tracker-entry-flow`.

| №   | Вопрос                          | Решение                                                                                                                      | Обоснование и следствие                                                               |
| --- | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 3.1 | Доступность быстрого добавления | Кнопка добавления операции доступна на вкладках Счета и Операции; скрыта на вкладках Аналитика и Настройки                   | Добавление доступно там, где пользователь думает об операциях, и не мешает настройкам |
| 3.2 | Порядок шагов формы             | При добавлении операции первым выбирается ее тип: доход, расход или перевод; набор остальных полей зависит от типа           | Тип определяет обязательные и недоступные поля, что уменьшает число ошибок ввода      |
| 3.3 | Обязательность категории        | Категория обязательна для дохода и расхода; для перевода категория не задается                                               | Совпадает с инвариантом транзакций уже реализованной модели данных                    |
| 3.4 | Дата операции                   | Дата операции по умолчанию текущая, пользователь может изменить ее и внести операцию задним числом                           | Поддерживается ввод пропущенных операций без отдельного режима импорта                |
| 3.5 | Поведение после сохранения      | После успешного сохранения закрыть форму, вернуться к исходному разделу, обновить операции и остаток, показать подтверждение | Пользователь видит эффект операции в остатке и не теряет место, откуда пришел         |

## Последствия

### Позитивные

- Границы первой версии замкнуты: у продукта нет планов/лимитов, импорта, синхронизации, конвертации и мультикнижности — каждый отказ снимает требования, а не откладывает их.
- Решения 1.3, 2.1, 2.2, 2.3, 3.3 и 4.4 согласуются с уже реализованной моделью данных (`initial_balance_minor`, `is_archived`, `kind`, `to_account_id`) и не требуют ее пересмотра.
- Аналитика и остатки получают единое правило: суммы сравниваются только внутри одной валюты, поэтому мультивалютность не требует курсов.
- Плоская навигация из четырех вкладок и кнопка добавления только на «Счета» и «Операции» задают предсказуемую структуру UI.
- Продуктовая семантика зафиксирована в одном месте: дальнейшие openspec-изменения можно выводить из этого ADR, не переспрашивая продуктовые вопросы.

### Ограничения, принятые осознанно

- Плановые бюджеты и сравнение план/факт не появятся без нового ADR: название `budget_tracker` этому не соответствует, и это ожидаемый разрыв между именем и продуктом.
- Банковские интеграции не рассматриваются, поэтому точность данных полностью зависит от ручного ввода.
- Конвертация валют отсутствует: пользователь видит раздельные итоги и не может получить одно общее число по всем счетам.
- Итоговая точность мультивалютного перевода зависит от введенных пользователем сумм; приложение показывает вычисленный фактический курс, но не проверяет его по внешнему источнику.

### Что требуется изменить в коде и артефактах (follow-up)

Ниже — следствия решений относительно текущего состояния репозитория. Ни один пункт не реализован на момент принятия ADR.

| Решение                                   | Текущее состояние                                                                                         | Что потребуется                                                                                                                                          |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 2.3 (мультивалютный перевод)              | `Transactions` содержит одну сумму `amountMinor`, `schemaVersion` 2                                       | Новая schema-версия: вторая сумма зачисления и/или сохраняемый вычисленный курс для перевода между счетами разных валют; обновление use case и валидации |
| 2.3, 1.2 (переводы вне доходов/расходов)  | Инварианты переводов и расчета баланса уже реализованы                                                    | Только фильтрация по `kind` в запросах аналитики                                                                                                         |
| 2.1, 2.5, 7.5 (группировка по валютам)    | `Accounts.currencyCode` — строка длиной 3, справочника валют нет                                          | Справочник валют и группировка агрегатов по `currencyCode` в запросах аналитики                                                                          |

### Конфликты и уточнения

- **Отмененное решение.** `openspec/changes/archive/2026-09-24-define-finance-data-model/design.md` фиксировал, что перевод между счетами в разных валютах не разрешается до появления модели курса. Решение 2.3 этот запрет отменяет: перевод разрешен, суммы списания и зачисления вводит пользователь, курс вычисляется. Для реализации потребуется новое openspec-изменение к модели транзакции; архивный `design.md` остается историческим документом и не переписывается.
- **Уточнение, а не конфликт.** `openspec/specs/local-finance-data-model/spec.md` уже требует, чтобы операция ссылалась не более чем на одну категорию и чтобы перевод не имел категории; решения 3.3 и 2.3 это подтверждают.
- **Локализация данных vs интерфейса.** Решение 5.1 расходится с правилом `app-foundation` о централизованной локализации пользовательских строк, если применить его к именам предустановленных банков: имя банка — это данные, а не строка интерфейса, и переводить его после первого запуска нельзя.
- **Fallback-локаль.** `app-foundation` использует `ru` как fallback locale, поэтому при неподдерживаемой локали устройства первый запуск даст российский предустановленный список банков — это ожидаемое поведение по решению 4.3.
