# ADR-0008: Документация архитектуры в формате C4

- **Статус:** Accepted
- **Дата:** 2026-10-03
- **Область:** документация, архитектура, структура каталогов, процесс ведения документации
- **Связанные артефакты:** `docs/architecture/ARCHITECTURE.md`, `docs/adr/0007-architecture-layers-and-directory-structure.md`, `README.md`, `openspec/config.yaml`, `openspec/specs/` (capability-спецификации), `openspec/changes/archive/` (архивные изменения)
- **Заменяет:** `docs/architecture-refactoring-plan.md` как носитель описания структуры и статуса рефакторинга

## Контекст

Рефакторинг архитектуры, завершенный в ADR-0007, описывался во временном плане
`docs/architecture-refactoring-plan.md`: он фиксировал слабые места, целевое
состояние и статус отдельных пунктов. После переноса кода в `lib/ui/` и
принятия ADR-0007 план устарел: он описывает структуру `presentation/`,
которой больше нет, а его «текущий статус» перестал отражать код.

Техническая документация хранится в `docs/`, а правила ведения ADR закреплены
в `openspec/config.yaml`. Оставалось нерешенным, где живет описание
**фактического** состояния архитектуры: план рефакторинга не годится
(он исторический), ADR фиксируют решения, а не текущее состояние кода, а
capability-спецификации OpenSpec описывают намерение, а не реализацию.
Нужен один документ, который показывает, как система устроена на самом деле.

## Решение

Текущее состояние архитектуры описывается в C4-модели
`docs/architecture/ARCHITECTURE.md`:

1. **C4-уровни** — System Context (системный контекст), Container view
   (уровень контейнеров) и Component view (уровень компонентов Flutter App)
   с диаграммами `mermaid` и поясняющими таблицами.
2. **Реконструкция из кода** — документ собирается из фактического дерева
   исходников, конфигурации и истории репозитория, а не из намерений;
   выводы, которых нет в коде, помечаются явно, OpenSpec трактуется как
   намерение.
3. **Проверка документации против реализации** — раздел несоответствий
   фиксирует, где документация (ADR, README, OpenSpec) расходится с кодом,
   а открытые вопросы — нерешенные архитектурные развилки.
4. **Разделение обязанностей** — ADR остаются журналом решений и их
   обоснования, OpenSpec — источником требований, а `ARCHITECTURE.md` —
   снимком фактической архитектуры; детали реализации, принадлежащие
   OpenSpec, в документ не дублируются.
5. **`docs/architecture-refactoring-plan.md`** — исторический план
   рефакторинга; он завершен и заменяется этим документом и ADR-0007,
   файл удаляется из репозитория.

## Альтернативы

- **Оставить план рефакторинга актуальным документом** — отклонено: план
  описывает уже не существующую структуру `presentation/` и смешивает
  «план» и «статус», что вводит в заблуждение.
- **Описывать фактическую архитектуру только в ADR** — отклонено: ADR —
  неизменяемые записи решений; текущее состояние кода меняется чаще, чем
  решения, и требует отдельного снимка.
- **Генерировать документацию только из кода без C4-структуры** — отклонено:
  без уровней и проверки намерение/факт документ не ответит на вопрос
  «как система устроена и где документация разошлась с кодом».

## Последствия

- Ссылки на `docs/architecture-refactoring-plan.md` из `README.md` заменяются
  ссылкой на `docs/architecture/ARCHITECTURE.md`.
- При изменении архитектуры обновляется `ARCHITECTURE.md` и, если меняется
  решение, создается новая ADR; несоответствия и открытые вопросы отражаются
  в соответствующих разделах документа.
- Историческая роль плана рефакторинга сохраняется в git-истории; новый
  документ ссылается на него как на исторический источник проверки.
- Затрагиваемые решения ADR-0007 (слои, зависимости, структура каталогов)
  не изменяются: они проверяются по коду в `ARCHITECTURE.md`, но остаются
  зафиксированными в ADR-0007.
