# ADR-0007: Архитектура слоев и структура каталогов

- **Статус:** Accepted
- **Дата:** 2026-10-03
- **Область:** архитектура, структура кода, организация слоев
- **Связанные артефакты:** `docs/architecture-refactoring-plan.md`, `README.md`

## Контекст

Приложение выросло из стартового шаблона Flutter: каталог `presentation/`
содержал страницы, виджеты и контроллеры в общей папке `providers/`,
инфраструктурный `core/` смешивал UI-концерны (роутер, тема) с composition
root (`di`, `l10n`), а отдельные use cases домена зависели от конкретных
классов слоя данных. Для дальнейшего развития нужны однозначные правила
размещения кода и допустимые направления зависимостей.

## Решение

### 1. Слои и структура каталогов

```text
lib/
├── main.dart                       # точка входа; composition root приложения
├── core/                           # инфраструктура уровня приложения (не UI)
│   ├── di/                         # composition root: провайдеры Riverpod
│   ├── l10n/                       # arb и сгенерированная локализация
│   └── licensing/                  # регистрация лицензий ресурсов
├── data/
│   ├── local/                      # database, files, mappers, seed
│   └── repositories/               # реализации интерфейсов репозиториев
├── domain/
│   ├── models/                     # модели по агрегатам
│   ├── inputs/                     # DTO входа (FinanceAccountInput и др.)
│   ├── repositories/               # интерфейсы репозиториев и сервисов
│   ├── services/                   # чистые бизнес-правила
│   ├── common/                     # validation_result, error_codes
│   └── usecases/                   # сценарии приложения
└── ui/
    ├── core/                       # общий UI: router, theme, utils, widgets
    └── features/
        └── [feature]/
            ├── view_models/        # контроллеры состояния (Riverpod)
            ├── views/              # страницы
            └── widgets/            # виджеты фичи
```

### 2. Допустимые направления зависимостей

- `data` → `domain` (модели, интерфейсы репозиториев);
- `ui` → `domain` (через use cases и контроллеры) и `ui` → `core`;
- `domain` не зависит ни от `data`, ни от `ui`;
- `core/di` и `main.dart` — composition root: единственные места, знающие
  все слои.

### 3. Состояние и управление зависимостями

Состояние и DI построены на Riverpod: провайдеры репозиториев и use cases
регистрируются в `core/di`, контроллеры фич — `AsyncNotifier`/`Notifier` в
`view_models`. Это адаптация MVVM: контроллер — ViewModel, а вью читает
состояние через провайдеры. Вью не обращаются к use cases и репозиториям
напрямую.

### 4. Модели домена

Модели разнесены по агрегатам: `finance_account.dart`, `finance_transaction.dart`,
`analytics_models.dart` и другие. `finance_models.dart` сохранен как
реэкспортирующая «бочка» для совместимости импортов; новый код импортирует
конкретные файлы.

## Обоснование

- Гибридная структура (UI — по фичам, Data/Domain — по типу) локализует
  изменения фичи и упрощает навигацию по коду.
- Запрет зависимости `domain` от `data`/`ui` держит бизнес-логику тестируемой
  без подмены инфраструктуры.
- Composition root в одном месте (`core/di`) делает граф зависимостей обозримым.
